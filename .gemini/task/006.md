# Tâche — Système de filtrage et d’agrégation des données climatiques par zones

## Contexte général

Tu interviens sur une application de datavisualisation climatique réalisée dans le cadre de la SAE 303 (BUT MMI).

Le projet est actuellement en transition :

- Les fausses données utilisées pour le prototypage vont être abandonnées
- Les graphiques devront désormais s’appuyer sur des **données réelles certifiées**
- Ces données proviennent directement de **Météo-France**
- Elles sont fournies au format CSV puis **importées dans une base de données**

Toutes les règles de développement, de structuration et d’écriture du code sont définies dans le fichier `AGENTS.md`.  
Elles doivent être respectées strictement, sans exception.

---

## Objectif de la tâche

Créer un **système de filtrage des données climatiques**, sous la forme d’un fichier dédié, dont le rôle est :

- De récupérer les **données brutes** depuis la base de données
- De les **regrouper par zones géographiques**
- De fournir des données structurées et exploitables par les graphiques de l’application

Ce système doit être générique, robuste et réutilisable pour plusieurs types de données climatiques.

---

## Structure de la base de données (vision globale)

La base de données contient actuellement **trois tables principales** :

### 1. Table `precipitations`

- Données de précipitations
- Enregistrements mensuels
- Sur une période longue (plusieurs décennies)

### 2. Table `rayonnements`

- Données de rayonnement solaire
- Enregistrements mensuels

### 3. Table `temperatures`

- Données de températures (minimales, maximales, etc.)
- Enregistrements mensuels

---

### Colonnes communes à toutes les tables

Chaque table contient au minimum les colonnes suivantes :

- `NUM_POSTE`  
  → Numéro de poste Météo-France

- `NOM_USEL`  
  → Identifiant / nom de la station météo

- `AAAAMM`  
  → Année et mois de la mesure (format AAAAMM)

Les autres colonnes contiennent les valeurs climatiques propres à chaque table.

---

## Principe d’analyse retenu dans l’application

Dans l’application, l’analyse des données ne se fait **ni par station individuelle**, ni par point brut.

Les données doivent être **regroupées par zones géographiques**, définies comme suit :

- **Basse-Terre**
- **Grande-Terre**
- **La Désirade**
- **Marie-Galante**

Chaque station météo appartient à **une seule zone**.

---

## Objectif fonctionnel du fichier de filtre

Le fichier à produire doit :

1. Récupérer les données brutes depuis les tables (`precipitations`, `rayonnements`, `temperatures`)
2. Associer chaque station météo (`NUM_POSTE` / `NOM_USEL`) à une **zone géographique**
3. Regrouper les données :
   - Par **zone**
   - Par **année**
   - Éventuellement par **mois**, selon les besoins futurs
4. Produire une structure de données exploitable par les graphiques Chart.js

---

## Contraintes fonctionnelles

- Le regroupement par zone est obligatoire
- Les données doivent rester traçables (zone, année, type de donnée)
- Le système doit pouvoir être utilisé :
  - Pour les températures
  - Pour les précipitations
  - Pour le rayonnement solaire
- Le fichier doit être conçu comme une **brique intermédiaire** entre la base de données et la couche de visualisation

---

## Contraintes techniques

- Le fichier doit être écrit en **PHP**
- Une responsabilité claire :
  - Récupération
  - Filtrage
  - Agrégation
- Aucune logique de rendu ou de graphique dans ce fichier
- Le code doit être :
  - Propre
  - Structuré
  - Lisible
  - Sans commentaires
- Aucune donnée fictive
- Les données doivent provenir exclusivement de la base de données

---

## Contraintes d’architecture

- Le fichier doit pouvoir être inclus ou appelé par :
  - Les scripts de graphiques
  - Les sections PHP
- Il doit être facilement extensible si :
  - De nouvelles zones sont ajoutées
  - De nouveaux types de données climatiques apparaissent
- La logique d’association **station → zone** doit être centralisée

---

## Livrables attendus

Tu dois fournir :

1. Le fichier PHP de filtrage / agrégation des données
2. La logique de regroupement par zones géographiques
3. Une structure de données finale claire, prête à être consommée par Chart.js

Le tout doit être directement exploitable dans l’application existante.

---

## Rappels essentiels

- Respect absolu de `AGENTS.md`
- Données réelles uniquement
- Aucune fausse donnée
- Aucune logique de visualisation
- Séparation stricte des responsabilités
- Lisibilité, robustesse et évolutivité prioritaires
